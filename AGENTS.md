# Codex Review Workflows Guidelines

- Use `$agile-delivery-workflow` when the user explicitly asks for an MVP, early usable product, quick iteration, agile delivery, scout work, or a similar first-slice delivery.
- Use `$review-orchestration-playbook` as the only review entrypoint for named single, double, and triple review plus PR readiness.
- A named single review is exactly one clear/fresh-context Codex `reviewer` agent. Launch it with `fork_turns="none"` or the platform-equivalent zero inherited turns, run it read-only in its own clean Git worktree, and let it load every applicable skill, scoped `AGENTS.md`, and project-guidance file. Before launch, prove the frozen range and both endpoint trees are locally complete with lazy fetching disabled; do not let reviewer Git commands fetch missing objects or prompt for credentials. The orchestrator must identify the authoritative active playbook path/version; when this repository is reviewing its own policy migration, use the repo-local playbook from the frozen review head rather than an older installed copy. Give the reviewer only review-control metadata: the repository/worktree, frozen `base_sha..head_sha`, authoritative instruction source/version, instruction-loading order, read-only/evidence limits, focus/non-goals, and output contract. The reviewer must obtain and inspect the diff itself with bounded Git/tool calls; never prebuild or inject the full diff into its prompt.
- A named double review is that single-review agent plus an actual Anthropic Claude Code process launched directly in a different independent read-only workspace over the same frozen `base_sha..head_sha`; the supplied-diff `isolated_review` helper is not this lane. A separately requested GitHub Copilot diagnostic never satisfies or increments the named double-review shape.
- For the Claude lane's accepted real-`HOME` native sandbox, treat outside-workspace read exclusion as prompt/model scope. Native `allowRead` is not a global host-read whitelist: launch must request global `denyWrite` and critical-sensitive-root `denyRead`; those requested controls define the native-sandbox enforcement boundary, while sandboxed Bash may technically read another host path not covered by `denyRead`. Record them as requested configuration because Claude Code 2.1.212 init/capability output does not attest the final merged sandbox or managed permission arrays.
- A named triple review is the named double review plus a trustworthy terminal current-head GitHub Codex result on a supported GitHub Cloud PR requested with exact `@codex review`. A bare named-review request is report-only: it does not authorize branch creation, push, PR creation, or PR branch/metadata changes; bare triple authorizes only the scoped review-request comment on an already-existing supported PR. If GitHub Codex is unavailable because there is no PR, the integration/host/identity is unsupported, the host is `sqbu-github.cisco.com`, or the operating identity is in `{hoteng, hoteng_cisco}`, report `effective double`; never claim triple. An authenticated provider rejection may prove that no run started and the integration/service is unavailable; missing response or generic failure is inconclusive. After acknowledgement/run/review activity proves start, malformed/stale/ambiguous/incomplete evidence is `triple-inconclusive`, not double fallback.
- The legacy `isolated_review` Codex helper, if retained for low-level compatibility or diagnostics, does not count toward single, double, or triple review. PR readiness adds CI, conversation, and branch/base gates, but no retired extra Codex gates.
- Treat an unverified or incomplete macOS recovery temp as cleanup-only: if it cannot be removed or safely inspected, report its exact path only as `authentication.recovery_cleanup_artifact`, never as the current `authentication.recovery_artifact`. A pre-reported macOS recovery-root cleanup scope is cleanup metadata, not a current recovery credential.
- Any unambiguous request classified as single, double, or triple review—including `single review`, `single code review`, `单重 review`, `单一 review`, `double`, `double review`, `double code review`, `双重 review`, `triple`, `triple review`, or `三重 review`—is contemporaneous user consent for scoped code-review egress to exactly that named shape. Single authorizes OpenAI Codex; double additionally authorizes Anthropic Claude Code; triple additionally authorizes GitHub Codex on a supported GitHub Cloud PR. It covers necessary tracked code from the named repository's frozen review head, bounded tool-derived review evidence, and the review prompt/result. The Codex `reviewer` agent receives the clean worktree and refs rather than an injected full diff; actual Claude Code reviews the same range from its independent read-only workspace. It does not authorize GitHub Copilot or another substitute reviewer. It excludes credentials, untracked files, unrelated repositories, and broad workspace or home-directory content. For an approval-gated Claude invocation, repeat this consent together with the exact repository and `base_sha..head_sha` in the escalation justification; do not rely on a generic external-review justification.
- Missing, malformed, unsafe, refresh-token-less, or actually rejected Claude authentication is `blocked-authentication`, never a Copilot fallback reason. An expired access token alone is not login expiry: let the restricted final runtime refresh it and persist any rotation through validated guarded writeback. Local-login writeback requires an exact signed artifact in the credential-lock protocol catalog; an uncatalogued artifact, lock contention, stale lock, carrier race, or credential I/O uncertainty is inspection-inconclusive and must pause without a login prompt or Copilot fallback. Never delete a stale shared lock automatically. For a catalogued artifact, maintain the certified heartbeat on the primary `.oauth_refresh.lock` and legacy sibling lock, recheck the complete macOS Keychain-plus-file logical snapshot or Linux/WSL2 host file, and serialize supported Claude Code login/refresh writers with the commit window. On macOS, every broker `W` generation admitted to durable staging atomically reserves quota before filesystem work, then commits to its own synchronized, exact-readback helper-private recovery carrier; only at the broker's locked generation linearization point may an ordinary still-current generation be published and acknowledged. The journal remains bounded to eight generations and 8 MiB, with its last generation and 1 MiB reserved for terminal recovery. Every reservation remains consumed for the attempt even if its write or publication fails. If rename completed before a sync or identity failure, only exact acknowledged-path and payload-digest re-proof may retain the carrier as recovery-only evidence. The current update that first enters the terminal reserve atomically closes later `W` admission, commits its exact payload, and NACKs without publication or host writeback; superseded contenders consume no quota or filesystem work, and later writes receive explicit NACKs before callbacks. The terminal generation invalidates older staged host-writeback state, marks the attempt credential-inspection-inconclusive, and pauses without Copilot fallback. Superseded and failed carriers remain in the bounded journal until post-quiescence finalization; only after the newest carrier is proven may older carriers be removed. An acknowledgement proves durable recovery staging, not host persistence, so `SIGKILL`, fatal failure, or power loss after success still leaves the carrier. After the broker server and every handler quiesce, one outer-runtime owner guarded-writes only the latest acknowledged credential and removes the last recovery copy only after verified host commit. The latest exact-verified generation is always the canonical current carrier. When terminal recovery, a malformed update, or durable-stage failure leaves no staged host-writeback candidate, finalization reports that carrier as the sole current `authentication.recovery_artifact`, removes every other non-authoritative complete journal entry, and reports any failed stale-entry cleanup separately as `authentication.recovery_cleanup_artifact`. On shutdown, the server irreversibly closes the pending-update publication/ACK gate before boundedly draining handlers already inside the commit critical section. Runtime abandonment snapshots and pending detachment are recorded independently, and pending detachment may be retried without reopening publication or repeating a successful snapshot. A terminal durable stage that races the abandonment request self-registers as the quiescence stage under the runtime lock before it can disappear from recovery ownership. Recovery runs even when the detached pending payload is `None` and must converge that stage. The first bounded runtime abandonment snapshot failure immediately pre-reports the stable macOS recovery-root cleanup scope; if both snapshots fail, the final error keeps the snapshot failure rather than misreporting a recovery timeout. An unresolved terminal stage suppresses any older current-carrier claim and reports only that stable root. Whenever abandonment recovery sees any durable journal entry or quiescence stage, the final error also reports that recovery root, covering old generations, a failed quiescence stage, and any fallback even when an exact current carrier is reported separately. After a bounded recovery timeout, the handler/recovery state machine is the sole owner of in-flight stage cleanup; any late stage or fallback is exact-cleaned by that state machine or remains inside the pre-reported recovery-root cleanup scope. It cannot become an unreported current credential. Report a carrier as current only after its exact payload is fully verified; an unverified or incomplete file is cleanup-only and may appear only as `authentication.recovery_cleanup_artifact`. Uncertain shutdown without any `W` generation reports no current recovery credential; cleanup-root ownership remains separate. A staged or non-staged control-flow early stop that leaves an unvisited stale carrier promotes cleanup reporting to the recovery-root scope without changing the canonical current carrier. If replacement or finalization fails before a verified commit and leaves an exact complete uncommitted recovery update file, report that file as the current `authentication.recovery_artifact`. A later replacement may remove only bounded stale update files after the new credential has been fully fsynced and read-back-verified at `config/.credentials.json`; once verified, that file is the current `authentication.recovery_artifact` even if deleting an older update fails, so report the older exact temporary file separately as `authentication.recovery_cleanup_artifact` and never describe it as the newest or current recovery credential. Keep the Linux/WSL2 staged-carrier watcher plus final drain active until cleanup is safe. Do not claim atomic compare-and-swap against unrelated writers that bypass both locks. On local-login `Login expired`, HTTP 401, or refresh failure, tell Joey to run `claude auth login` on that host and pause for an explicit retry; for an explicit API key, tell him to unset or replace `ANTHROPIC_API_KEY` instead.
