# Codex Review Workflows Guidelines

- For catalogued low-level-helper Claude local-login artifacts, acquire the certified host refresh locks before the first credential read and hold one transaction lease through credential exposure, runtime refresh, process or broker quiescence, final drain, and verified host commit. Release only after a safe terminal state. If quiescence or persistence is unproven, abandon the lease, retain the shared lock directories as a stale fence, report the authoritative recovery identity, and pause without Copilot fallback or automatic lock deletion. An explicit API key or OAuth token bypasses this helper-only local-login transaction; the named direct Claude lane never inherits it.
- Use `$agile-delivery-workflow` when the user explicitly asks for an MVP, early usable product, quick iteration, agile delivery, scout work, or a similar first-slice delivery.
- Use `$review-orchestration-playbook` as the only review entrypoint for named single, double, and triple review plus PR readiness.
- A named single review is exactly one clear/fresh-context Codex `reviewer` agent. Launch it with `fork_turns="none"` or the platform-equivalent zero inherited turns, run it read-only in its own clean detached Git workspace produced by the trusted pre-status materializer, and let it load every applicable skill, scoped `AGENTS.md`, and project-guidance file. Before launch, prove the frozen range and both endpoint trees are locally complete with lazy fetching disabled; do not let reviewer Git commands fetch missing objects or prompt for credentials. The orchestrator must identify the authoritative active playbook path/version. For a self-policy migration, candidate-head Markdown may be read as review subject and scoped guidance, but the parent-owned reviewer profile, prompt, `materialize-worktree`, `validate-worktree`, compatible-version/provenance preflight, Claude launcher, and stream validator/schema must come from an independently trusted bundle pinned outside the candidate head/range; record that bundle's absolute source path, version, and SHA-256 digest. The guard must load only the manifest-bound runtime source bytes, never expose a bundle directory to ordinary import resolution, and never consume bytecode or native extension substitutes. If no compatible trusted guard exists, bootstrap under the prior trusted policy, merge and release the candidate, and only then activate the new guard; never execute candidate-head Python or shell as review-control bootstrap. Give the reviewer only review-control metadata: the repository/worktree, frozen `base_sha..head_sha`, materialization/validation receipt, trusted-bundle identity, exact sanitized Git argv prefix, instruction-loading order, read-only/evidence limits, focus/non-goals, and output contract. The reviewer must obtain and inspect the diff itself with bounded Git/tool calls; never prebuild or inject the full diff into its prompt.
- A named double review is that single-review agent plus an actual Anthropic Claude Code process launched directly in a different independent read-only clean detached Git workspace over the same frozen `base_sha..head_sha`; the supplied-diff/private-Git `isolated_review` helper is not this lane. The direct lane uses trusted real `HOME` through the canonical local-login-only interface described below. A separately requested GitHub Copilot diagnostic never satisfies or increments the named double-review shape.
- The canonical Claude Code compatibility range is `>=2.1.211,<3.0.0`, defined once in `skills/review-orchestration-playbook/scripts/review_runtime/claude_version_policy.py`. Exact patch versions belong in signed per-version artifact or schema evidence, not in global eligibility policy; Claude Code `2.1.212` is the audited stream-schema baseline, not a global pin. Every selected version must pass publisher provenance, the mandatory credential-free `--help` capability probe, accepted parent-private preflight evidence and digest bindings, and strict stream-contract gates before it can supply findings.
- Immediately before either local named lane starts, invoke `materialize-worktree` and then `validate-worktree` through a parent-validated absolute Python interpreter with `-I -B -S`, the source-only absolute guard path in the recorded trusted bundle, and the contract's fixed clean environment against that lane's exact frozen base/head and owner-private absent destination. The materializer must isolate config, attributes, hooks, fsmonitor, filters, submodules, remotes, and object dependencies before it initializes the private repository, imports the exact hard-bounded reachable-object closure, and performs detached checkout; never use `git worktree add`, clone/fetch/upload-pack, or a pre-validator status query. The validator's forced status must be the first status operation. Never execute the guard directly, resolve Python from ambient `PATH`, load global or user site initialization, or resolve a bare repository-relative `scripts/named_lane_guard`. Any repository-visible `include.path` or `includeIf.*.path` is `blocked-safety`; evaluate other safety-relevant Git values from direct local configuration with includes disabled. Launch the exact revalidated actual Claude executable only through that same trusted interpreter and guard's process-only `run-claude` subcommand; its test-oriented timeout, stream, and prompt overrides may only retain or tighten the production caps. Load the parent-recorded trusted `$review-orchestration-playbook` source for the property-scoped materialization, symlink, interpreter, process-bound, failure, and non-guarantee contract.
  The materializer must also bind the exact source `.git` marker/admin/common/object directories and linked-worktree back-pointer, reject suffix-DWIM, shallow, alternate, and promisor sources, cap object count/logical bytes/checkout entries and bytes/compressed pack bytes, prove the private destination inventory equals the frozen base/head closure, force/persist Git-false commit-graph and multi-pack-index consumption, and run bounded full object-validity `fsck` before checkout. Treat the resolved fixed-path Git executable as a declared trust root rather than claiming the guard validates its publisher identity.
- For the Claude lane's accepted real-`HOME` native sandbox, treat outside-workspace read exclusion as prompt/model scope. Native `allowRead` is not a global host-read whitelist: launch must request global `denyWrite` and critical-sensitive-root `denyRead`; those requested controls define the native-sandbox enforcement boundary, while sandboxed Bash may technically read another host path not covered by `denyRead`. Record them as requested configuration because capability output and `system/init` evidence—including the audited Claude Code 2.1.212 baseline—do not attest the final merged sandbox or managed permission arrays.
- Capture canonical Claude raw stdout outside the model-visible worktree and require the trusted bundle's `named_lane_guard validate-claude-stream` profile, launched through the recorded absolute Python interpreter with `-I -B -S`, to return `classification: accepted` for the exact parent-private preflight result, cwd, model, fixed local-login authentication source, and child return code before any findings count. That profile raw-loads the manifest-bound validator, compatibility profile, audited schema baseline, and capability-contract evidence; binds their digests; selects the reviewed closed legacy or extended stream profile for the preflight-selected version; and validates every admitted intermediate event against the selected closed, session-bound contract before checking the terminal result. Direct execution of `validate_claude_stream.py` is compatibility-only. Prose inspection, partial output, or an ad hoc parser never satisfies the lane; validator acceptance still does not prove the merged sandbox.
- A named triple review is the named double review plus complete authenticated current-scope GitHub Codex evidence requested with exact `@codex review` on exact host `github.com`; every other host, including `sqbu-github.cisco.com` and every GitHub Enterprise host, and every operating identity in `{hoteng, hoteng_cisco}` is unsupported. Evaluate the full provider snapshot only through `skills/review-orchestration-playbook/references/github-codex-evidence-authority.md` and record `request_policy`, `provider_profile`, and `evidence_basis`. The producer waits for both local lanes to become terminal, may post at most one same-head request, and must never post a second or third request. An early request records `early-request-observed`; more than one same-scope request records `duplicate-observed`, including when the extra request overlaps or remains pending. Those warnings are outcome-neutral and never authorize a repair request. A lone compliant pending request is not a warning; it means the provider outcome is still pending unless a trustworthy terminal artifact already exists. Clean completion under `terminal-payload` requires a complete terminal provider-authored current-head findings payload, and only exact REST `user.login == "chatgpt-codex-connector[bot]"` with exact `user.type == "Bot"` plus the authority's fixed clean/finding/inline-parent grammar can supply it; every other terminal-looking exact-provider payload is malformed. Under the authority profiles, terminal payload controls `mixed` regardless of reaction ordering: a later reaction, including `eyes` or `+1`, never overturns a trustworthy current-scope terminal payload, and `mixed` never accepts reaction-only clean. Only `thumbs-up-clean` can reach the complete weak `+1` fallback. Each of its 3–10 historical samples comes from a distinct non-current scope and, together with the separately validated current snapshot, binds one selected exact `@codex review` parent request to its individual child exact-bot `+1` by IDs, URLs, immutable scope, server times, and strict ordering, enumerates every accepted same-scope request plus its fully paginated reactions so a request newer than the selected parent or a cross-parent conflict cannot be hidden, and binds provider declaration identity/digest. The selected `+1` parent is the unique latest request by semantic time. `eyes` is liveness-only and affects only reaction-only fallback: an `eyes` at or after the selected `+1` prevents weak clean but never changes terminal selection. `unknown` cannot pass reaction-only evidence and remains pending while bounded waiting is meaningful, then inconclusive. Fetch the selected review body plus every fully paginated associated inline review comment, or the complete terminal issue-comment body, and include relevant thread state in the final re-read. Exact `app.slug == "chatgpt-codex-connector"` check/run evidence is service-start evidence only and never completes triple or proves clean/no-findings. If the PR merge base changes after a request while the head stays unchanged, invalidate the old whole-PR evidence but do not post a replacement same-head request; report readiness `blocked-input` (`base-changed-same-head`) and effective `triple-inconclusive` until a separately authorized ordinary change creates a new head. Never manufacture an empty or anchor commit merely to regain GitHub-lane eligibility.
- Historical and current reaction evidence are not one sample pool. `thumbs-up-clean` requires 3–10 eligible historical outcomes from distinct non-current scopes; the exact current scope is validated separately and never counts toward that minimum. Each historical sample and the separate current snapshot binds the selected request/reaction parent relationship and the complete same-scope request audit. Declaration authority comes only from the canonical GitHub REST issue-comment resource re-fetched unchanged with exact `user.login == "chatgpt-codex-connector[bot]"`, `user.type == "Bot"`, `performed_via_github_app.slug == "chatgpt-codex-connector"`, exact repository/PR/API-URL/HTML-URL bindings, and the exact `If Codex has suggestions, it will comment; otherwise it will react with 👍.` line. Generic issuer/source fields, caller-supplied records, and self-hashed paraphrases do not qualify.
- The GitHub lane report uses `request_policy.status: compliant | warning | unknown | not-applicable`; use `not-applicable` only when no eligible request plane exists. A proved pre-provider ineligibility or blocker has `provider_profile: null` and `evidence_basis: null`. An eligible wait has a computed profile (or `unknown`) and null basis. An accepted terminal clean/findings result records `terminal-payload` or `mixed` plus its selected basis; accepted weak reaction clean records `thumbs-up-clean` plus its complete reaction basis. An inconclusive result records its computed profile (or `unknown`) and a stable blocking basis when one exists, otherwise null.
- Resolve the local range and PR selector independently: preserve an explicit frozen range for local lanes, while an explicitly named PR or exactly one authenticated open-PR candidate for the exact current head repository/branch selects PR-specific/triple work. Explicit-range-only single/double requires no PR probe. Multiple required PR candidates leave the GitHub/PR-specific lane `blocked-input` until the caller names a PR; a frozen range does not select among them, although fully scoped local lanes may run. For every selected PR, independently read `baseRefName`, `baseRefOid`, and `headRefOid`; with lazy fetching disabled, require both endpoint commits locally and require `git merge-base --all pr_base_oid pr_head_oid` to produce exactly one `pr_merge_base`. A selected PR's explicit frozen range satisfies PR-specific readiness or triple completion only when `base_sha == pr_merge_base` and `head_sha == pr_head_oid`. A same-head/different-base range is `blocked-input` (`scope-mismatch`): preserve the caller's range, do not silently rewrite it, and never describe its local review results as whole-PR coverage. Explicit-range-only standalone single/double with no selected PR is unaffected. A proven no-PR result does not supply a range; require an explicit committed range or explicitly named target/base and never guess it. For triple, detached HEAD or unknown head ownership without an explicit PR is `blocked-input` / `triple-inconclusive`, not effective double; the fully scoped local lanes may still run. A bare named-review request is report-only and does not authorize branch creation, an anchor commit, push, PR creation, or PR branch/metadata changes. Reserve `blocked-authorization` for intended dirty/untracked state that would require an unauthorized anchor commit.
- Every selected PR, including one named explicitly, must also report exact lifecycle `state == "open"`, `merged == false`, and `merged_at == null` before local PR-specific lanes or third-lane work. Missing/contradictory lifecycle evidence is `blocked-input` (`pr-lifecycle-unverified`) and triple-inconclusive; closed-unmerged is `selected-pr-closed` and may reduce only an otherwise fully scoped, never-started third lane to effective double; merged is terminal `already-merged` / `selected-pr-merged`. Revalidate lifecycle before posting `@codex review`, before accepting its result, and before readiness/merge. An observed non-open lifecycle at any mandated snapshot after request/service start invalidates evidence and remains triple-inconclusive. These point-in-time snapshots do not prove that no intermediate close-and-reopen occurred between them.
- For each selected PR's first range freeze, persist immutable parent-owned `range_origin.kind`, `range_origin.base_sha`, and `range_origin.head_sha`; the kind is exactly `caller-supplied` or `pr-derived`, and original caller endpoints are never overwritten. On a post-request base-only retarget, apply the playbook's machine-readable state contract before generic `scope-mismatch`: stale, unknown-origin, or unauthorized parent-rewrite state stops before local lanes; a caller-supplied exact-current recovery or valid PR-derived exact-current rederivation may rerun the local lanes, but the same-head GitHub lane remains `triple-inconclusive` and no second request is allowed.
- Bare triple authorizes only the scoped review-request comment on an already-existing supported PR. Every selected existing PR still requires intended-head/current-head alignment before local lanes or readiness-state consumption, even when an unsupported host or identity has already reduced triple to effective double. Explicit-range-only standalone single/double has no selected PR and requires no comparison; authenticated actual PR absence likewise has none. If a still-eligible PR's current `headRefOid` does not equal the frozen `head_sha` and mutation is not separately authorized, leave it unchanged and report requested triple/effective triple-inconclusive with GitHub lane status `blocked-authorization`. For the same mismatch on an already unsupported PR, keep `requested: triple`, `effective: double`, and report readiness `blocked-authorization`; do not treat the mismatch as making the already-unavailable lane triple-inconclusive or as permitting readiness to continue. If GitHub Codex is unavailable because there is no PR or the host/identity is unsupported, report `effective double`; never claim triple. Classify no-start, liveness, terminal findings, and clean evidence from the complete provider snapshot under the evidence authority. The fixed baseline has an empty accepted structured capability/installation schema set and no accepted no-start body grammar, so integration/service uncertainty and free-form provider prose cannot prove unavailability. When no complete `thumbs-up-clean` reaction fallback is accepted, missing terminal evidence or an unestablished reaction-only profile remains pending while bounded waiting is meaningful; after exhaustion, generic failure, an unstable `unknown` profile, or an incomplete final re-read is inconclusive.
- The legacy `isolated_review` Codex helper, if retained for low-level compatibility or diagnostics, does not count toward single, double, or triple review. PR readiness adds CI, conversation, and branch/base gates, but no retired extra Codex gates.
- The low-level `isolated_review` helper retains its helper-private credential staging, lock, guarded-writeback, and recovery contracts in `helper-contract.md` and `claude-runtime-trust.md`. Those guarantees do not apply to the named direct Claude lane: its only active authentication interface is ordinary local login in trusted real `HOME`, including credential refresh and possible cache or tool-result artifacts. The direct lane accepts no API-key or OAuth-token environment interface; validator/schema recognition of `ANTHROPIC_API_KEY` is compatibility evidence only and does not make that launch mode available. When refresh is forbidden or local login is unavailable, report `blocked-authentication`. Do not claim helper broker/carrier guarantees or that `--no-session-persistence` makes real `HOME` immutable.
- Any unambiguous request classified as single, double, or triple review—including `single review`, `single code review`, `单重 review`, `单一 review`, `double`, `double review`, `double code review`, `双重 review`, `triple`, `triple review`, or `三重 review`—is contemporaneous user consent for scoped code-review egress to exactly that named shape. Single authorizes OpenAI Codex; double additionally authorizes Anthropic Claude Code; triple additionally authorizes GitHub Codex on an exact-host `github.com` PR. The selected reviewer is a trusted processor and may inspect the named repository's original tracked diff, necessary tracked context, bounded tool-derived evidence, and review prompt/result, including tracked repository secrets. The Codex `reviewer` agent receives the clean worktree and refs rather than an injected full diff; actual Claude Code reviews the same range from its independent read-only workspace. Do not redact, rewrite, or suppress tracked reviewer input because of a secret-delta result. This consent does not authorize GitHub Copilot or another substitute reviewer, automatic discovery of reviewer/runtime authentication credentials, untracked files, unrelated repositories, or broad workspace/home-directory content. For an approval-gated Claude invocation, repeat this consent together with the exact repository and `base_sha..head_sha` in the escalation justification; do not rely on a generic external-review justification.
- Secret-delta analysis never blocks a named reviewer launch; it is an independent PR/master admission control. Count each exact raw secret byte value globally over the complete base and head tracked trees, including raw Git path bytes, regular-file blobs, and symlink-target bytes, and allow `head_count <= base_count`. Only a first appearance or count growth blocks admission; unchanged values, deletions, and moves pass. Do not derive Base64, hex, URL-encoded, or other transformed variants; this is an explicit detection limitation. A genuinely incomplete bounded scan is `inconclusive`, and violation output lists only head-side added locations, not unchanged occurrences.
- PR/master exact-secret admission uses `isolated_review secret-admission --repo <repo> --base-ref <base_sha> --head-ref <head_sha>`. This direct Git-tree scan has `review_contract: admission-only-no-reviewer`, does not materialize a workspace, diff, or prompt, and never starts a reviewer. Only exit `0` (`clean`) with `temporary_cleanup_status: complete` permits admission; exit `1` means proved violations and remains `1` even if later location mapping or temporary cleanup is incomplete, while exit `75` means an inconclusive scan or a clean scan whose temporary cleanup failed. A head change invalidates the result. The retained `stateful final` / `stateful admission` pair belongs only to an explicitly chosen low-level helper run and is never a required PR-readiness producer.
