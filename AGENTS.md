# Codex Review Workflows Guidelines

- Use `$review-orchestration-playbook` as the only entrypoint for named single, double, and triple review plus PR readiness. Detailed schemas and evidence rules belong to the Skill, its canonical authority reference, and the machine contracts; do not duplicate them here.
- Preserve an explicit caller range independently from PR selection. Explicit-range-only single or double review bypasses selected-PR gates.
- For every selected PR, classify authenticated lifecycle first. Only exact `state == "open"`, `merged == false`, and `merged_at == null` may proceed to base/head/merge-base scope, retarget handling, local lanes, GitHub POST, or readiness. A post-start non-open observation remains invalid after reopen.
- Single is one fresh-context Codex reviewer in an independent trusted-guard-materialized clean read-only workspace. Double adds actual Claude Code in a second independent workspace over the same frozen range. Triple adds the eligible GitHub Codex lane; helper or Copilot runs never increment the named shape.
- For self-policy migration, use compatible review-control code from a trusted bundle pinned outside the candidate range. Candidate Markdown may be review subject, but candidate-head control code must not certify itself. Route local lanes through canonical `skills/review-orchestration-playbook/scripts/named_lane_guard` and its `validate-worktree` profile; the Skill and reference own the exact invocation and safety semantics.
- Treat one GitHub review epoch and all of its machine-authorized serial attempts as one logical named lane. Attempts provide orchestration, liveness, retry, and audit history; they are not provider-evidence authority.
- Complete the GitHub lane through the canonical provider and Action-status authorities. The consumer installs one sole-job caller using `JoeyTeng/codex-review-gate-action/.github/workflows/codex-review-gate.yml@v1`; treat that floating ref as a pre-execution trust boundary, then follow [github-pr-probes.md](skills/review-orchestration-playbook/references/github-pr-probes.md). Exact-attempt `W` must equal receipt `job.workflow_sha`, receipt `action.ref`, and the unique exact-attempt `referenced_workflows[].sha`, whose ref is exact `refs/tags/v1`; candidate `C` is cross-bound through the controlled checkout, receipt `action.commit_sha`, provenance `action.commit_oid`, and provenance `tags.v1.peeled_commit_oid`. Every release candidate independently fetches and locally OpenPGP-verifies its provenance-bound release-`R`, derived-`v1.minor`, and historical-`v1`-`T` tag objects targeting its `C`; the separate final-stable current alias `T_current/C_current` is live audit evidence and never validates historical proof. Candidate-local `workflow_sha_resolution` maps `W` matches as zero = `proved-incompatible` with otherwise complete proof, one = eligible, and more than one = malformed `ERROR`; missing/invalid/ambiguous/unverifiable tag proof or any integrity/cross-binding contradiction makes the whole admission `ERROR`. Exclude only proved-incompatible candidates and require exactly one valid GitHub Release with one provenance-v2 asset; `v1.5.0` is never admitted and `v1.5.1` is first admitted. Keep provenance source commit separate and treat independently authenticated source-to-Action subtree equality as admission proof. Complete release triage and the sealed composite reduction coordinate remain owned by the canonical authority/machine; the epoch machine alone owns the exact evidence-resource configuration, while one parent-owned composed-operation ledger applies it. Never patch-pin the generic Skill. This is run-level consistency, not cryptographic job attestation: rejection cannot undo floating-`@v1` code already executed with caller permissions, and there is no online or post-publication revocation guarantee. Applicable current-head or parent-proved-ancestor findings and unresolved threads block. Only the sealed reduction's exact current-head required `codex/review-gate` success, after that same coordinate binds provider validation and the epoch/marker clocks, is Action-status `PASS`; a noncanonical repository-side compatibility publisher, context/head/state coincidence, description, creator, check run, or `eyes` cannot supply it, while `+1` supplies neither `PASS` nor ACK. Report `request_policy`, `provider` (the sole owner of `evidence_basis`), `required_action_status`, `named_github_lane`, `reaction_audit`, and `readiness` as six independent planes.
- Keep that required-status producer caller per-PR. A separate repository-owned scheduled dispatcher may perform bounded per-PR transport only; it is not producer evidence, `PASS`, or an alternate caller, and its trigger, cadence, and permissions are not generic protocol.
- Never blind-retry an uncertain POST, reinterpret a late artifact into another epoch, or manufacture an empty or anchor commit to restore GitHub-lane eligibility. The same-head base-only-retarget blocker exists because head-bound provider evidence cannot prove coverage of the new merge base.
- The named-direct Claude lane uses publisher-verified compatible Claude Code with ordinary local login in trusted real `HOME`. The low-level `isolated_review` helper has separate authentication, credential-staging, and recovery contracts; never project those guarantees onto the named-direct lane.
- Named review consent authorizes only the selected processors and the scoped tracked repository evidence for the requested shape. Secret-delta admission is a separate PR/master gate and does not redact or suppress tracked reviewer input.
- A report-only named-review request authorizes no mutation except the bare-triple request-comment flow: on an eligible existing PR it may post the scoped `@codex review` comment and only those serial attempts permitted by the canonical epoch machine. It still does not authorize branch creation, commits, push, PR creation, PR metadata mutation, an anchor commit, fixes, delivery, or merge. PR readiness adds current-head CI, conversation, authorization, branch/base, and final lifecycle gates, but no retired review lanes.
