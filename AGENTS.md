# Codex Review Workflows Guidelines

- Use `$agile-delivery-workflow` when the user explicitly asks for an MVP, early usable product, quick iteration, agile delivery, scout work, or a similar first-slice delivery.
- Use `$review-orchestration-playbook` as the only review entrypoint for named single, double, and triple review plus PR readiness.
- A named single review is exactly one clear/fresh-context Codex `reviewer` agent. Launch it with `fork_turns="none"` or the platform-equivalent zero inherited turns, run it read-only in its own clean Git worktree, and let it load every applicable skill, scoped `AGENTS.md`, and project-guidance file. Before launch, prove the frozen range and both endpoint trees are locally complete with lazy fetching disabled; do not let reviewer Git commands fetch missing objects or prompt for credentials. The orchestrator must identify the authoritative active playbook path/version. For a self-policy migration, candidate-head Markdown may be read as review subject and scoped guidance, but the parent-owned reviewer profile, prompt, `validate-worktree`, and launcher must come from an independently trusted bundle pinned outside the candidate head/range; record that bundle's absolute source path, version, and SHA-256 digest. The guard must load only the manifest-bound runtime source bytes, never expose a bundle directory to ordinary import resolution, and never consume bytecode or native extension substitutes. If no compatible trusted guard exists, bootstrap under the prior trusted policy, merge and release the candidate, and only then activate the new guard; never execute candidate-head Python or shell as review-control bootstrap. Give the reviewer only review-control metadata: the repository/worktree, frozen `base_sha..head_sha`, trusted-bundle identity, exact sanitized Git argv prefix, instruction-loading order, read-only/evidence limits, focus/non-goals, and output contract. The reviewer must obtain and inspect the diff itself with bounded Git/tool calls; never prebuild or inject the full diff into its prompt.
- A named double review is that single-review agent plus an actual Anthropic Claude Code process launched directly in a different independent read-only workspace over the same frozen `base_sha..head_sha`; the supplied-diff `isolated_review` helper is not this lane. A separately requested GitHub Copilot diagnostic never satisfies or increments the named double-review shape.
- Immediately before either local named lane starts, invoke `validate-worktree` through a parent-validated absolute Python interpreter with `-I -B -S`, the source-only absolute guard path in the recorded trusted bundle, and the contract's fixed clean environment against that lane's exact clean frozen worktree/head; never execute the guard directly, resolve Python from ambient `PATH`, load global or user site initialization, or resolve a bare repository-relative `scripts/named_lane_guard`. Any repository-visible `include.path` or `includeIf.*.path` is `blocked-safety`; evaluate other safety-relevant Git values from direct local/per-worktree configuration with includes disabled. Before any status or reviewer Git command, require direct `core.fsmonitor` to be unset or Git-false. Launch the exact revalidated actual Claude executable only through that same trusted interpreter and guard's process-only `run-claude` subcommand; its test-oriented timeout, stream, and prompt overrides may only retain or tighten the production caps. Load the active `$review-orchestration-playbook` for the narrow symlink, interpreter, process-bound, failure, and non-guarantee contract.
- For the Claude lane's accepted real-`HOME` native sandbox, treat outside-workspace read exclusion as prompt/model scope. Native `allowRead` is not a global host-read whitelist: launch must request global `denyWrite` and critical-sensitive-root `denyRead`; those requested controls define the native-sandbox enforcement boundary, while sandboxed Bash may technically read another host path not covered by `denyRead`. Record them as requested configuration because Claude Code 2.1.212 init/capability output does not attest the final merged sandbox or managed permission arrays.
- A named triple review is the named double review plus a trustworthy terminal current-head GitHub Codex result on a supported GitHub Cloud PR requested with exact `@codex review`. A bare named-review request is report-only: it does not authorize branch creation, push, PR creation, or PR branch/metadata changes; bare triple authorizes only the scoped review-request comment on an already-existing supported PR. If GitHub Codex is unavailable because there is no PR, the integration/host/identity is unsupported, the host is `sqbu-github.cisco.com`, or the operating identity is in `{hoteng, hoteng_cisco}`, report `effective double`; never claim triple. An authenticated provider rejection may prove that no run started and the integration/service is unavailable only when it is tied to the exact request/dispatch or satisfies the sole-unresolved fallback; an exact SHA alone does not bind one of multiple unresolved same-head requests. Missing response or generic failure is inconclusive. After acknowledgement/run/review activity proves start, malformed/stale/ambiguous/incomplete evidence is `triple-inconclusive`, not double fallback.
- The legacy `isolated_review` Codex helper, if retained for low-level compatibility or diagnostics, does not count toward single, double, or triple review. PR readiness adds CI, conversation, and branch/base gates, but no retired extra Codex gates.
- The low-level `isolated_review` helper retains its helper-private credential staging, lock, guarded-writeback, and recovery contracts in `helper-contract.md` and `claude-runtime-trust.md`. Those guarantees do not apply to the named direct Claude lane: its only authentication interface is ordinary local login in trusted real `HOME`, including the CLI's own credential refresh. The direct lane accepts neither an API-key nor an OAuth-token interface; when refresh is forbidden or local login is unavailable, report `blocked-authentication`. Do not claim helper broker/carrier guarantees.
- Any unambiguous request classified as single, double, or triple review—including `single review`, `single code review`, `单重 review`, `单一 review`, `double`, `double review`, `double code review`, `双重 review`, `triple`, `triple review`, or `三重 review`—is contemporaneous user consent for scoped code-review egress to exactly that named shape. Single authorizes OpenAI Codex; double additionally authorizes Anthropic Claude Code; triple additionally authorizes GitHub Codex on a supported GitHub Cloud PR. The selected reviewer is a trusted processor and may inspect the named repository's original tracked diff, necessary tracked context, bounded tool-derived evidence, and review prompt/result, including tracked repository secrets. The Codex `reviewer` agent receives the clean worktree and refs rather than an injected full diff; actual Claude Code reviews the same range from its independent read-only workspace. Do not redact, rewrite, or suppress tracked reviewer input because of a secret-delta result. This consent does not authorize GitHub Copilot or another substitute reviewer, automatic discovery of reviewer/runtime authentication credentials, untracked files, unrelated repositories, or broad workspace/home-directory content. For an approval-gated Claude invocation, repeat this consent together with the exact repository and `base_sha..head_sha` in the escalation justification; do not rely on a generic external-review justification.
- Secret-delta analysis never blocks a named reviewer launch; it is an independent PR/master admission control. Count each exact raw secret byte value globally over the complete base and head tracked trees, including raw Git path bytes, regular-file blobs, and symlink-target bytes, and allow `head_count <= base_count`. Only a first appearance or count growth blocks admission; unchanged values, deletions, and moves pass. Do not derive Base64, hex, URL-encoded, or other transformed variants; this is an explicit detection limitation. A genuinely incomplete bounded scan is `inconclusive`, and violation output lists only head-side added locations, not unchanged occurrences.
- When low-level `isolated_review` state supplies PR/master evidence, `stateful final --state-dir <state_dir>` produces the reviewer artifact and `stateful admission --state-dir <state_dir>` independently evaluates the same current-head state. Only admission exit `0` (`clean`) permits admission; exit `1` means violations, exit `3` pending, and exit `75` inconclusive. A head change invalidates both results.
