# Codex Review Workflows

## Named Review At A Glance

`review-orchestration-playbook` is the single entrypoint for named review and PR readiness. It keeps local range review, GitHub PR selection, provider evidence, and delivery gates distinct.

| Requested shape | Logical lanes |
| --- | --- |
| Single | One fresh-context Codex reviewer in an independent clean read-only workspace |
| Double | Single plus one actual Claude Code process in a second independent workspace over the same frozen range |
| Triple | Double plus the eligible GitHub Codex lane on an existing exact-host `github.com` PR |

Six stable rules define the public contract:

1. Preserve an explicit caller range independently from PR selection. Explicit-range-only single or double review needs no PR. For a selected PR, classify lifecycle first; only then derive base/head/merge-base scope and apply retarget or mismatch policy.
2. Local named lanes share one committed range but use separate trusted-guard-materialized workspaces. Self-policy migrations take review control from a compatible trusted bundle outside the candidate range.
3. One GitHub review epoch and all machine-authorized serial attempts are one logical named lane. Never blind-retry uncertain transport, overlap controlled requests, or manufacture an empty or anchor commit.
4. GitHub evidence is finding-first. Current-head and proved-ancestor findings plus unresolved applicable threads block; proved nonancestors are excluded from the current decision, while unknown ancestry never passes. A carrier-valid, stable current-head clean may supersede only an older same-head or ancestor threadless finding; an ancestor-bound clean alone remains pending because current-head clean evidence is absent. Hashless issue-comment clean supplies no positive fallback, `+1` supplies neither `PASS` nor ACK, and `eyes` remains ACK/liveness-only.
5. The consumer wires one sole-job caller to `JoeyTeng/codex-review-gate-action/.github/workflows/codex-review-gate.yml@v1`. That floating major ref is a pre-execution trust boundary. After execution, exact-attempt `W` is cross-bound through receipt `job.workflow_sha`, receipt `action.ref`, and the unique exact-attempt `referenced_workflows[].sha`, whose ref is exact `refs/tags/v1`; candidate `C` is cross-bound through the controlled checkout, receipt `action.commit_sha`, provenance `action.commit_oid`, and provenance `tags.v1.peeled_commit_oid`. Every release candidate independently fetches and locally OpenPGP-verifies its provenance-bound release-`R`, derived-`v1.minor`, and historical-`v1`-`T` tag objects targeting its `C`. The separate final-stable current alias `T_current/C_current` is live audit evidence and never historical proof. Candidate-local `workflow_sha_resolution` maps `W` matches as zero = `proved-incompatible` with otherwise complete proof, one = eligible, and more than one = malformed `ERROR`; missing/invalid/ambiguous/unverifiable tag proof or any integrity/cross-binding contradiction makes the whole admission `ERROR`. Select exactly one valid GitHub Release with one provenance-v2 asset; keep the source commit separate and require independently authenticated source-to-Action subtree equality as admission proof. `v1.5.0` is never admitted, while `v1.5.1` is first admitted. The canonical authority/machine owns complete release-candidate triage and the sealed composite reduction coordinate; the epoch machine alone owns the exact evidence-resource configuration, while one parent-owned composed-operation ledger applies it. The consumer pins neither selected called-workflow bytes/digest nor the selected release's external Action SHA set; the generic Skill freezes protocol/schema/policy majors and the trusted signer, not a patch SHA or workflow blob. This is run-level consistency, not cryptographic job attestation: rejection cannot undo floating-`@v1` code already executed with caller permissions, and there is no online or post-publication revocation guarantee. `PASS` means only the sealed reduction's exact current-head required Commit Status `codex/review-gate == success` after that coordinate also binds final provider validation and the epoch/marker clocks. A noncanonical repository-side compatibility publisher cannot satisfy `PASS`, even when context, head, state, description, or creator appears to match. Report `request_policy`, `provider` (the sole owner of `evidence_basis`), `required_action_status`, `named_github_lane`, `reaction_audit`, and `readiness` as six independent planes.
   That producer caller is per-PR. An independent repository-owned scheduled dispatcher may provide bounded per-PR transport into it, but the dispatcher is not producer evidence, `PASS`, or an alternate producer caller; its exact trigger, cadence, and permissions remain repository policy rather than generic protocol.
6. PR readiness is a separate current-head delivery gate over the required Action status, authorization, local validation, exact-secret admission, all other required CI, conversations, branch/base state, and final lifecycle/scope. A report-only named-review request authorizes no mutation except the bare-triple request-comment flow: on an eligible existing PR it may post the scoped `@codex review` comment and only those serial attempts permitted by the canonical epoch machine. It still does not authorize branch creation, commits, push, PR creation, PR metadata mutation, fixes, delivery, or merge.

## Low-Level `isolated_review` Helper Only

Everything below this heading through the synthetic-fixture note documents the low-level `isolated_review` helper. It records `review_contract: supplied-diff-private-git` and `named_lane_eligible: false`, materializes its supplied diff and bounded Git objects in a helper-owned detached worktree backed by private minimal Git, and defaults to a clean committed head. Only explicit `--include-source-wip` may capture a digest-bound composite of staged, unstaged, and nonignored untracked state; that WIP result is diagnostic and never PR-readiness evidence. Its executable snapshots, outer sandboxes, `/auth` carrier, credential brokers, credential-lock catalog, guarded writeback, recovery artifacts, and historical supplemental fallback are not requirements or guarantees of the canonical direct Claude lane and cannot satisfy named double or triple review. The canonical lane instead follows the ordinary real-`HOME` authentication/runtime control-plane and selected-deny contracts linked from the named review shapes above.

The helper's production app-server input contains the complete authenticated primary diff plus a deterministic bounded set of changed regular UTF-8 text blobs from the head tree. It inspects at most the first 128 size-eligible candidates in raw Git-path order, skips binary content and paths the evidence format cannot represent, and retains at most 32 files, 64 KiB per file, and 512 KiB total. The checkout worker authenticates every retained blob in the evidence manifest, and the reviewer launch reopens and verifies the exact worktree files before passing their paths as nearby context; any retained manifest, ordering, content, or identity drift fails closed.

The helper's external ChatGPT auth carrier records paired wall-clock and suspend-aware monotonic baselines when it authenticates the owner-only source. Linux and WSL use `CLOCK_BOOTTIME`; Darwin uses `mach_continuous_time`. Every later sample and state update occurs under one evidence lock. The high-water record rejects any monotonic rollback and wall rollback beyond the one-second sampling-skew tolerance, commits the latest effective wall time before checking expiry, and never drops a high water after a failed lifetime check. Time spent asleep is therefore charged, and neither retry order nor the tolerance can restore or extend token lifetime.

For catalogued local-login artifacts, that low-level helper serializes the complete host refresh transaction, not only final writeback. It acquires the certified host locks before reading either macOS carrier or the Linux/WSL2 credential file, then keeps the same lease across credential exposure, network refresh, durable staging, supervised-process or broker quiescence, final drain, and verified host commit. A second helper waits before credential exposure and re-reads the host state only after acquiring the lease. Safe completion releases the lease; unproven quiescence or persistence deliberately leaves the shared lock directories as a stale fence and pauses with recovery diagnostics. Helper authentication precedence is `ANTHROPIC_API_KEY` > `CLAUDE_CODE_OAUTH_TOKEN` > local login; either explicit source is opaque-forwarded and bypasses this local-login transaction.

After its separate helper-only workspace, sandbox, and authentication preparation, the helper passes captured raw Claude stdout through the same canonical strict stream validator. It binds the selected compatible version and parent-selected authentication source, applies the closed legacy or extended init/intermediate/terminal profile, and accepts findings only from `classification: accepted`; helper-only broker or carrier evidence never substitutes for this output contract.

Publisher verification means the fixed Anthropic signing key, signed per-version manifest, and matching binary checksum. Native Mach-O/ELF checks reject script/interpreter wrappers and incompatible platform artifacts, but cannot distinguish every native launcher; publisher identity comes only from the signed manifest and exact artifact digest. Before that verification, the candidate's self-reported version runs with a fixed credential-free environment that does not inherit proxy URLs, custom CA paths, authentication material, or review metadata. After verification, the helper copies the candidate into a private, checksum-keyed executable snapshot. Every model attempt reuses only that snapshot for capability probes, post-provenance dependency inspection, credentials, review data, and the final Claude process.

The fixed-path native GPG source is a separately validated host-trust dependency, not evidence of Anthropic publisher provenance. The helper holds its stable file descriptor, copies the main executable into a fresh current-user `0700` home below an explicit helper-owned private `0700` root, publishes that copy as a `0500` execution snapshot, and uses the snapshot for all key conversion, fingerprint listing, and signature-verification calls. That main-file snapshot does not by itself freeze dynamic libraries: on macOS, sealed system endpoints terminate traversal as platform TCB while every non-sealed Homebrew branch is recursively captured and rechecked under the explicit `admin` boundary; the main executable must name exactly the standard `/usr/lib/dyld` loader and dependencies may not name another loader. Linux/WSL2 accepts only root-owned `/usr/bin/gpg{,2}` by default, proves that the loader-visible ELF `PT_DYNAMIC` table maps consistently through exactly one file-backed `PT_LOAD` at byte and loader-page granularity, rejects other page-rounded load mappings over the dynamic table, rejects `DT_RPATH`/`DT_RUNPATH` and audit-module tags, validates the architecture-specific canonical glibc loader, invokes that loader directly with `--list`, captures both loader-visible symlink chains and resolved root-owned endpoints, and rebuilds the exact closure through the same loader before every call. The host-GPG boundary never executes an implementation-variable `ldd` script. Security-sensitive host tools receive fixed minimal environments rather than inherited loader, shell, or compiler controls. Positive WSL2 classification requires an explicit WSL2 kernel identity marker and bounded `/proc/self/mountinfo` provenance checks. `/run/WSL`, `WSL_INTEROP`, distro environment, and binfmt evidence prove only WSL presence because those surfaces also exist under WSL1. A custom kernel without a recognizable WSL2 marker is unsupported whenever any WSL-presence signal remains. If every such signal is also removed, the guest is observationally indistinguishable from native Linux and follows the Linux classification; the common Linux/WSL mount guard still rejects positive DrvFS/Windows provenance through custom automounts, bind mounts, or aliases. Positively identified WSL2 also keeps the fast literal `/mnt/<drive>` rejection.

Linux and WSL2 use a separate inner file-tool boundary because the trusted Claude runtime must read either its staged `/auth/config` credential or an API key while model-invoked tools must not. The helper uses `dontAsk`, exposes only `Read`, allows only `Read(./**)`, rejects file-mention syntax in the review prompt, and denies every non-workspace synthetic-root mount with absolute double-slash rules such as `Read(//auth/**)` and `Read(//proc/**)`. The dedicated writable `/auth` carrier root lets the verified runtime create both its primary lock inside `/auth/config` and its legacy sibling `/auth/config.lock`; no host credential is mounted there. Command construction fails closed if a future mount lacks deny coverage or is added below `/workspace`. The outer `bubblewrap` sandbox still enforces host filesystem, process, write, and network isolation; the staged credential carrier is not a confidentiality boundary from the Claude process that authenticates with it.

Low-level helper Claude authentication is validated without an OAuth warmup or a future-attempt lifetime reservation. An expired access token alone is not login expiry. On macOS, the helper safely reads both the documented Keychain item and the empirically compatible credential file under the current account's `pwd` home, selects the structurally valid credential with the later expiry, and exposes either source only through the same capability-authenticated temporary broker. When both carriers contain the same refresh token, they are treated as one logical login even when their access tokens or expiry metadata differ. Every `W` generation admitted to durable staging atomically reserves space before filesystem work in an attempt-scoped journal bounded to eight generations and 8 MiB of payload. The last generation and 1 MiB are reserved for terminal recovery, and every reservation remains consumed for the attempt even when later write or publication fails. Each admitted generation commits to a distinct helper-private recovery carrier whose credential, directories, synchronized rename, and exact readback are verified. If rename completed before a sync or identity failure, only exact acknowledged-path and payload-digest re-proof may retain that carrier as recovery-only evidence. Ordinary still-current generations are published and acknowledged only at the broker's locked linearization point. The current update that first enters the terminal reserve atomically closes later `W` admission, commits its exact payload into the final slot, and returns a NACK without publication or host writeback; superseded contenders consume no quota or filesystem work, and later writes receive explicit NACKs before callbacks. The terminal generation invalidates older staged host-writeback state, marks credential inspection inconclusive, and pauses without Copilot fallback. Superseded and failed carriers remain within the bounded journal for the attempt rather than being deleted by a later publication. Acknowledgement proves durable recovery staging, not host persistence, so helper `SIGKILL`, fatal failure, or power loss after success still leaves the carrier. On shutdown, the server first irreversibly closes its pending-update publication/ACK gate, then boundedly drains handlers that already entered the commit critical section. Runtime abandonment snapshots and pending detachment are tracked independently, so detachment can be retried without reopening publication or repeating a successful snapshot. A terminal durable stage racing the abandonment request self-registers as the quiescence stage under the runtime lock. Recovery executes even when the detached pending payload is `None` and still converges that stage. The first bounded runtime abandonment snapshot failure immediately pre-reports the stable macOS recovery-root cleanup scope; if both snapshots fail, the helper pauses with the snapshot failure rather than misclassifying it as recovery timeout. An unresolved terminal stage suppresses any older current-carrier claim and reports only that stable root. Whenever abandonment recovery observes any durable journal entry or quiescence stage, the final error also reports that recovery root, so old generations, a failed quiescence stage, and any fallback retain visible ownership even when an exact current carrier is separately reported. If bounded recovery itself times out, the handler/recovery state machine remains the sole owner of in-flight stage cleanup. A late stage or fallback is exact-cleaned by that state machine or remains within the pre-reported recovery-root cleanup scope; it cannot silently become an unreported current credential. Recovery metadata names a current carrier only after exact payload verification; any unverified or incomplete file is cleanup-only. Uncertain shutdown without a `W` generation reports no current recovery credential; cleanup-root ownership remains separate. After the broker server and every handler quiesce, one outer-runtime owner detaches and guarded-writes only the latest acknowledged credential, proves the newest durable carrier before removing older journal entries, and deletes the final recovery copy only after verified host commit. The latest exact-verified generation is always the canonical current carrier. When terminal recovery, a malformed update, or durable-stage failure leaves no staged host-writeback candidate, finalization reports that carrier as the sole current `authentication.recovery_artifact`, removes every other non-authoritative complete journal entry, and reports any failed stale-entry cleanup separately as `authentication.recovery_cleanup_artifact`. A staged or non-staged control-flow early stop that leaves any stale carrier unvisited promotes cleanup reporting to the recovery-root scope without changing the canonical current carrier. A file-first dual-carrier commit reads back an ambiguous Keychain result, retries one exact file-new/Keychain-old state once, and otherwise preserves the rotated file credential while pausing as inspection-inconclusive; it never rolls back to a refresh token that rotation may already have invalidated. If broker or handler quiescence cannot be proven, or required post-quiescence host writeback cannot be completed, the outer-runtime owner retains the newest verified durable carrier or durably materializes a newer pending structurally valid payload before reporting its path, then pauses without Copilot fallback. If recovery replacement or finalization fails before a verified commit and leaves an exact complete uncommitted update file, the helper reports that file in `authentication.recovery_artifact` as the current recovery credential. A later replacement may remove only bounded stale update files after the new credential has been fully fsynced and read-back-verified at `config/.credentials.json`; once verified, that file is `authentication.recovery_artifact` even if deleting an older update fails, so the helper reports the older exact temporary file separately as `authentication.recovery_cleanup_artifact` and never as the newest or current recovery credential. On Linux and WSL2, the helper stages a private copy of the validated host credential and a bounded watcher persists each stable rotation during the attempt, followed by a synchronous final drain before cleanup. If Claude exits after rotating the staged credential but before releasing its helper-owned locks, a normal supervisor return plus watcher join proves writer quiescence; only then may the helper preflight the exact empty `0700` staged primary and legacy lock directories, remove them in reverse acquisition order, and retry the final drain once. A timeout, process leak, unsafe lock, failed retry, or guarded host-write failure instead retains the private recovery carrier inside the review container, reports its path without credential contents, and pauses without Copilot fallback.

Low-level helper local-login refresh writeback is enabled only for exact signed artifacts in the helper's credential-lock protocol catalog. The initial catalog covers Claude Code `2.1.211` for Darwin arm64/x64 and Linux glibc/musl arm64/x64; WSL2 reuses the matching Linux artifact. Within the shared publisher-verified `>=2.1.211,<3.0.0` range, the low-level helper remains usable with an explicit API key or OAuth token, while an uncatalogued helper local-login artifact pauses as inspection-inconclusive before credentials or review data are exposed. For a catalogued artifact, the parent keeps Claude's primary `.oauth_refresh.lock` and legacy sibling lock fresh with the certified 5-second heartbeat, captures both macOS carriers' existence/digest plus the file identity, rechecks both under the locks, and performs guarded writeback only when the complete logical snapshot still matches. Linux/WSL2 applies the same certified lock protocol to its staged and host files. Concurrent supported Claude Code login/refresh writers therefore serialize with the commit window, observed host changes win, and refresh-token rotation is normally retained. A stale shared host lock is never deleted automatically; the helper pauses for controlled cleanup only after the operator confirms that no writer remains. The narrowly scoped staged-carrier recovery above does not apply to a host credential directory. This is not an atomic compare-and-swap guarantee against unrelated external writers that bypass both Claude locks.

For the low-level helper, missing, malformed, unsafe, refresh-token-less, `Login expired`, HTTP 401, or refresh failure is `blocked-authentication`: the helper pauses instead of falling back to Copilot, and tells the operator to run `claude auth login` for local login or unset/replace the winning explicit `ANTHROPIC_API_KEY` or `CLAUDE_CODE_OAUTH_TOKEN`, as applicable. Only stderr and structured primary error fields are failure-classification evidence; repository-controlled partial result text can never authorize a model or Copilot fallback. Lock contention, carrier races, I/O uncertainty, and an uncatalogued lock protocol are inspection-inconclusive and do not imply a bad login. The low-level helper's compatibility Copilot backend requires a separate explicit supplemental request and never satisfies named double review.

An incomplete or exact-readback-unverified macOS recovery temp is cleanup residue, not a recoverable credential. If it cannot be removed or safely inspected, the helper reports its exact path only as `authentication.recovery_cleanup_artifact`; only a fully verified complete uncommitted update or a verified committed replacement may be `authentication.recovery_artifact`. A pre-reported recovery-root cleanup scope is cleanup metadata and does not claim that a current recovery credential exists.

`synthetic-token-fixtures` selects exact authoring values from the review helper's fixed finite catalog. The helper catalog remains the only enforcement authority; skill templates contain placeholders only.

## Test

The helper requires Python 3.10 or later; CI pins the minimum supported runtime.

```bash
python3 -B -c 'import pathlib, sys; [compile(pathlib.Path(path).read_bytes(), path, "exec") for path in sys.argv[1:]]' skills/review-orchestration-playbook/scripts/isolated_review skills/review-orchestration-playbook/scripts/named_lane_guard skills/review-orchestration-playbook/scripts/review_runtime/*.py
python3 -B -m unittest discover -s skills/review-orchestration-playbook/tests
```

Ordinary discovery runs the compact cross-platform suite. CI runs the two
platform-neutral giant contracts once in a dedicated Ubuntu matrix gate. Run
either one locally by setting `CODEX_REVIEW_RUN_GIANT_CONTRACTS=1` and invoking
its exact `test_contracts.RepositoryContractTest...` selector.
