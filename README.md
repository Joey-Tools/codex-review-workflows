# Codex Review Workflows

Public review orchestration, synthetic fixture selection, and local delivery gate skills.

For catalogued local-login artifacts, the helper serializes the complete host refresh transaction, not only final writeback. It acquires the certified host locks before reading either macOS carrier or the Linux/WSL2 credential file, then keeps the same lease across credential exposure, network refresh, durable staging, supervised-process or broker quiescence, final drain, and verified host commit. A second helper waits before credential exposure and re-reads the host state only after acquiring the lease. Safe completion releases the lease; unproven quiescence or persistence deliberately leaves the shared lock directories as a stale fence and pauses with recovery diagnostics. API-key mode does not enter this local-login transaction.

`review-orchestration-playbook` is the single entrypoint for policy-bound local Codex review, Claude-family double review, GitHub Codex triple review, and PR readiness. Claude Code model selection remains pinned, while CLI compatibility follows a publisher-verified release range and explicit macOS, Linux, and WSL2 capability contract documented in [Claude Runtime Trust And Platform Capabilities](skills/review-orchestration-playbook/references/claude-runtime-trust.md).

Publisher verification means the fixed Anthropic signing key, signed per-version manifest, and matching binary checksum. Native Mach-O/ELF checks reject script/interpreter wrappers and incompatible platform artifacts, but cannot distinguish every native launcher; publisher identity comes only from the signed manifest and exact artifact digest. Before that verification, the candidate's self-reported version runs with a fixed credential-free environment that does not inherit proxy URLs, custom CA paths, authentication material, or review metadata. After verification, the helper copies the candidate into a private, checksum-keyed executable snapshot. Every model attempt reuses only that snapshot for capability probes, post-provenance dependency inspection, credentials, review data, and the final Claude process.

The fixed-path native GPG source is a separately validated host-trust dependency, not evidence of Anthropic publisher provenance. The helper holds its stable file descriptor, copies the main executable into a fresh current-user `0700` home below an explicit helper-owned private `0700` root, publishes that copy as a `0500` execution snapshot, and uses the snapshot for all key conversion, fingerprint listing, and signature-verification calls. That main-file snapshot does not by itself freeze dynamic libraries: on macOS, sealed system endpoints terminate traversal as platform TCB while every non-sealed Homebrew branch is recursively captured and rechecked under the explicit `admin` boundary; the main executable must name exactly the standard `/usr/lib/dyld` loader and dependencies may not name another loader. Linux/WSL2 accepts only root-owned `/usr/bin/gpg{,2}` by default, proves that the loader-visible ELF `PT_DYNAMIC` table maps consistently through exactly one file-backed `PT_LOAD` at byte and loader-page granularity, rejects other page-rounded load mappings over the dynamic table, rejects `DT_RPATH`/`DT_RUNPATH` and audit-module tags, validates the architecture-specific canonical glibc loader, invokes that loader directly with `--list`, captures both loader-visible symlink chains and resolved root-owned endpoints, and rebuilds the exact closure through the same loader before every call. The host-GPG boundary never executes an implementation-variable `ldd` script. Security-sensitive host tools receive fixed minimal environments rather than inherited loader, shell, or compiler controls. Positive WSL2 classification requires an explicit WSL2 kernel identity marker and bounded `/proc/self/mountinfo` provenance checks. `/run/WSL`, `WSL_INTEROP`, distro environment, and binfmt evidence prove only WSL presence because those surfaces also exist under WSL1. A custom kernel without a recognizable WSL2 marker is unsupported whenever any WSL-presence signal remains. If every such signal is also removed, the guest is observationally indistinguishable from native Linux and follows the Linux classification; the common Linux/WSL mount guard still rejects positive DrvFS/Windows provenance through custom automounts, bind mounts, or aliases. Positively identified WSL2 also keeps the fast literal `/mnt/<drive>` rejection.

Linux and WSL2 use a separate inner file-tool boundary because the trusted Claude runtime must read either its staged `/auth/config` credential or an API key while model-invoked tools must not. The helper uses `dontAsk`, exposes only `Read`, allows only `Read(./**)`, rejects file-mention syntax in the review prompt, and denies every non-workspace synthetic-root mount with absolute double-slash rules such as `Read(//auth/**)` and `Read(//proc/**)`. The dedicated writable `/auth` carrier root lets the verified runtime create both its primary lock inside `/auth/config` and its legacy sibling `/auth/config.lock`; no host credential is mounted there. Command construction fails closed if a future mount lacks deny coverage or is added below `/workspace`. The outer `bubblewrap` sandbox still enforces host filesystem, process, write, and network isolation; the staged credential carrier is not a confidentiality boundary from the Claude process that authenticates with it.

Claude authentication is validated without an OAuth warmup or a future-attempt lifetime reservation. An expired access token alone is not login expiry. On macOS, the helper safely reads both the documented Keychain item and the empirically compatible credential file under the current account's `pwd` home, selects the structurally valid credential with the later expiry, and exposes either source only through the same capability-authenticated temporary broker. When both carriers contain the same refresh token, they are treated as one logical login even when their access tokens or expiry metadata differ. Every `W` generation admitted to durable staging atomically reserves space before filesystem work in an attempt-scoped journal bounded to eight generations and 8 MiB of payload. The last generation and 1 MiB are reserved for terminal recovery, and every reservation remains consumed for the attempt even when later write or publication fails. Each admitted generation commits to a distinct helper-private recovery carrier whose credential, directories, synchronized rename, and exact readback are verified. If rename completed before a sync or identity failure, only exact acknowledged-path and payload-digest re-proof may retain that carrier as recovery-only evidence. Ordinary still-current generations are published and acknowledged only at the broker's locked linearization point. The current update that first enters the terminal reserve atomically closes later `W` admission, commits its exact payload into the final slot, and returns a NACK without publication or host writeback; superseded contenders consume no quota or filesystem work, and later writes receive explicit NACKs before callbacks. The terminal generation invalidates older staged host-writeback state, marks credential inspection inconclusive, and pauses without Copilot fallback. Superseded and failed carriers remain within the bounded journal for the attempt rather than being deleted by a later publication. Acknowledgement proves durable recovery staging, not host persistence, so helper `SIGKILL`, fatal failure, or power loss after success still leaves the carrier. On shutdown, the server first irreversibly closes its pending-update publication/ACK gate, then boundedly drains handlers that already entered the commit critical section. Runtime abandonment snapshots and pending detachment are tracked independently, so detachment can be retried without reopening publication or repeating a successful snapshot. A terminal durable stage racing the abandonment request self-registers as the quiescence stage under the runtime lock. Recovery executes even when the detached pending payload is `None` and still converges that stage. The first bounded runtime abandonment snapshot failure immediately pre-reports the stable macOS recovery-root cleanup scope; if both snapshots fail, the helper pauses with the snapshot failure rather than misclassifying it as recovery timeout. An unresolved terminal stage suppresses any older current-carrier claim and reports only that stable root. Whenever abandonment recovery observes any durable journal entry or quiescence stage, the final error also reports that recovery root, so old generations, a failed quiescence stage, and any fallback retain visible ownership even when an exact current carrier is separately reported. If bounded recovery itself times out, the handler/recovery state machine remains the sole owner of in-flight stage cleanup. A late stage or fallback is exact-cleaned by that state machine or remains within the pre-reported recovery-root cleanup scope; it cannot silently become an unreported current credential. Recovery metadata names a current carrier only after exact payload verification; any unverified or incomplete file is cleanup-only. Uncertain shutdown without a `W` generation reports no current recovery credential; cleanup-root ownership remains separate. After the broker server and every handler quiesce, one outer-runtime owner detaches and guarded-writes only the latest acknowledged credential, proves the newest durable carrier before removing older journal entries, and deletes the final recovery copy only after verified host commit. The latest exact-verified generation is always the canonical current carrier. When terminal recovery, a malformed update, or durable-stage failure leaves no staged host-writeback candidate, finalization reports that carrier as the sole current `authentication.recovery_artifact`, removes every other non-authoritative complete journal entry, and reports any failed stale-entry cleanup separately as `authentication.recovery_cleanup_artifact`. A staged or non-staged control-flow early stop that leaves any stale carrier unvisited promotes cleanup reporting to the recovery-root scope without changing the canonical current carrier. A file-first dual-carrier commit reads back an ambiguous Keychain result, retries one exact file-new/Keychain-old state once, and otherwise preserves the rotated file credential while pausing as inspection-inconclusive; it never rolls back to a refresh token that rotation may already have invalidated. If broker or handler quiescence cannot be proven, or required post-quiescence host writeback cannot be completed, the outer-runtime owner retains the newest verified durable carrier or durably materializes a newer pending structurally valid payload before reporting its path, then pauses without Copilot fallback. If recovery replacement or finalization fails before a verified commit and leaves an exact complete uncommitted update file, the helper reports that file in `authentication.recovery_artifact` as the current recovery credential. A later replacement may remove only bounded stale update files after the new credential has been fully fsynced and read-back-verified at `config/.credentials.json`; once verified, that file is `authentication.recovery_artifact` even if deleting an older update fails, so the helper reports the older exact temporary file separately as `authentication.recovery_cleanup_artifact` and never as the newest or current recovery credential. On Linux and WSL2, the helper stages a private copy of the validated host credential and a bounded watcher persists each stable rotation during the attempt, followed by a synchronous final drain before cleanup. If Claude exits after rotating the staged credential but before releasing its helper-owned locks, a normal supervisor return plus watcher join proves writer quiescence; only then may the helper preflight the exact empty `0700` staged primary and legacy lock directories, remove them in reverse acquisition order, and retry the final drain once. A timeout, process leak, unsafe lock, failed retry, or guarded host-write failure instead retains the private recovery carrier inside the review container, reports its path without credential contents, and pauses without Copilot fallback.

Local-login refresh writeback is enabled only for exact signed artifacts in the helper's credential-lock protocol catalog. The initial catalog covers Claude Code `2.1.211` for Darwin arm64/x64 and Linux glibc/musl arm64/x64; WSL2 reuses the matching Linux artifact. The broader publisher-verified `>=2.1.211,<3.0.0` range remains usable with an explicit API key, while an uncatalogued local-login artifact pauses as inspection-inconclusive before credentials or review data are exposed. For a catalogued artifact, the parent keeps Claude's primary `.oauth_refresh.lock` and legacy sibling lock fresh with the certified 5-second heartbeat, captures both macOS carriers' existence/digest plus the file identity, rechecks both under the locks, and performs guarded writeback only when the complete logical snapshot still matches. Linux/WSL2 applies the same certified lock protocol to its staged and host files. Concurrent supported Claude Code login/refresh writers therefore serialize with the commit window, observed host changes win, and refresh-token rotation is normally retained. A stale shared host lock is never deleted automatically; the workflow pauses for controlled cleanup only after the operator confirms that no writer remains. The narrowly scoped staged-carrier recovery above does not apply to a host credential directory. This is not an atomic compare-and-swap guarantee against unrelated external writers that bypass both Claude locks.

Missing, malformed, unsafe, refresh-token-less, `Login expired`, HTTP 401, or refresh failure is `blocked-authentication`: the workflow pauses instead of falling back to Copilot, and tells the operator to run `claude auth login` for local login or unset/replace an explicit `ANTHROPIC_API_KEY`, as applicable. Only stderr and structured primary error fields are failure-classification evidence; repository-controlled partial result text can never authorize a model or Copilot fallback. Lock contention, carrier races, I/O uncertainty, and an uncatalogued lock protocol are inspection-inconclusive and do not imply a bad login. Copilot fallback remains available, with existing consent, only when the secure Claude runtime is deterministically absent/unavailable or Claude model entitlement blocks the pinned model chain.

An incomplete or exact-readback-unverified macOS recovery temp is cleanup residue, not a recoverable credential. If it cannot be removed or safely inspected, the helper reports its exact path only as `authentication.recovery_cleanup_artifact`; only a fully verified complete uncommitted update or a verified committed replacement may be `authentication.recovery_artifact`. A pre-reported recovery-root cleanup scope is cleanup metadata and does not claim that a current recovery credential exists.

`synthetic-token-fixtures` selects exact authoring values from the review helper's fixed finite catalog. The helper catalog remains the only enforcement authority; skill templates contain placeholders only.

python3 -m py_compile skills/review-orchestration-playbook/scripts/isolated_review skills/review-orchestration-playbook/scripts/review_runtime/*.py
