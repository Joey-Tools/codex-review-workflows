## Canonical Review Shapes

These are the only meanings of the named review shapes. Count completed logical reviewer lanes, never retries, model fallbacks, helper processes, or delivery gates.

| Requested shape | Required lanes |
| --- | --- |
| Single / single review / single internal review | One fresh-context Codex reviewer. |
| Double / double review / local double review | Single plus one actual Claude Code reviewer. |
| Triple / triple review | Double plus one logical GitHub Codex lane bound to the exact review epoch on an exact-host `github.com` PR. A formal-broad automatic/manual/controlled trigger enters the epoch, machine-authorized serial attempts remain inside that one lane, and the six report planes remain independent. |

PR readiness means the effective review shape plus CI, unresolved-conversation, base/head, and merge-policy checks. It does not add a hidden reviewer lane.

### GitHub Codex fallback

GitHub Codex is the optional third lane, so its unavailability changes a requested triple review into an effective double review.

- Under the fixed baseline, only a proven missing PR, unsupported host, or unsupported operating identity establishes third-lane unavailability. The fixed authority baseline has no accepted no-start body grammar and an empty accepted structured capability/installation schema set, so integration/service state remains unknown rather than unavailable. A missing response remains pending while bounded waiting is meaningful; after receipt-proved exhaustion, timeout, generic request/HTTP failure, or guessed integration state is inconclusive rather than unavailable.
- The only supported host is exact `github.com`. Every other host is unsupported, including `sqbu-github.cisco.com` and every GitHub Enterprise host.
- PRs whose operating identity is in `{hoteng, hoteng_cisco}` are unsupported for this lane.
- Delegate provider record grammar, closed status mapping, terminal classification, Action-status producer binding, and transitions to [github-codex-evidence-authority.md](references/github-codex-evidence-authority.md) and [github-codex-review-epoch-state-machine.json](references/github-codex-review-epoch-state-machine.json); do not reproduce their fields or status enum in this Skill. Procedurally, reconcile the complete current-scope provider snapshot and its liveness captures before any POST, retry, or result decision. Exact-App current-head checks/runs remain liveness-only. The reducer accepts only one parent-owned sealed composite coordinate that binds required-status membership, final provider validation, the immutable epoch-origin clock, and the current marker/attempt state; the six report planes are independent outputs, not independent reducer authorities, and caller dictionaries or standalone projections cannot replace that coordinate. Only the exact current-head required `codex/review-gate == success` selected through that reduction is Action-status `PASS`; a noncanonical repository-side compatibility publisher or a match inferred from context, head, state, description, or creator is insufficient. `PASS` alone is neither a provider artifact nor proof of completed triple or merge readiness. Unknown or conflicting identity, head, pagination, ancestry, or producer authority fails closed as the canonical resources direct.
- Install the required-status producer once as a consumer-owned caller that preserves that repository's events, permissions, and concurrency and contains exactly one job using `JoeyTeng/codex-review-gate-action/.github/workflows/codex-review-gate.yml@v1`. Floating `@v1` is an explicitly accepted pre-execution trust boundary, not an immutable launch pin. After execution, use [github-pr-probes.md](references/github-pr-probes.md) and the canonical authority to validate producer receipt v1, producer protocol major 1, decision schema 1, decision policy major 1, and release-provenance v2. Derive exact-attempt `W` only from receipt `job.workflow_sha`, receipt `action.ref`, and the unique exact-attempt `referenced_workflows[].sha`, with exact ref `refs/tags/v1`. For every release candidate, independently fetch and locally OpenPGP-verify its provenance-bound immutable release tag object `R`, derived `v1.minor` tag object, and historical provenance-`v1` tag object `T`, each directly targeting that candidate's `C`. Its closed `workflow_sha_resolution` compares `W` with only historical `T` and exact `C`: zero matches is `proved-incompatible` only with otherwise complete valid unambiguous proof, one is eligible, and more than one is malformed `ERROR`. Independently authenticate and final-stably reread the separate current floating alias `T_current -> C_current`; it is live audit/stability evidence and never supplies exact-attempt `W` or validates a historical candidate. If `W == T_current`, additionally require `C_current == C`; a valid later alias move may otherwise differ. Classify the complete authenticated release-candidate vector as exactly `valid`, `proved-incompatible`, or `malformed-or-incomplete-error`. Complete unambiguous evidence that proves a compatibility predicate false—including a valid OpenPGP signature by one unambiguous nontrusted primary signer or zero `W` matches—is `proved-incompatible`; missing, invalid, ambiguous, or unverifiable tag/signature evidence, multiple `W` matches, and every integrity or cross-binding contradiction make the whole admission `ERROR`. Exclude only proved-incompatible candidates and require exactly one valid release with all three tag proofs and exactly one GitHub-digest-bound provenance-v2 asset. `v1.5.0` is never admitted and has no erratum path; `v1.5.1` is the first admitted semantic boundary. Retain exact SemVer `policy_version` only as audit evidence, require its major to be 1, and enforce the canonical cross-source equality; receipt v1 supplies no `policy_version`. Keep caller-workflow SHA, run/event head, PR/status head, `W`, candidate `R/T/C`, and current alias `T_current/C_current` separate. Provenance `source.commit_oid` identifies the distinct source-repository commit; source-to-Action subtree equality is independently authenticated admission proof. The consumer pins neither selected called-workflow bytes/digest nor the selected release's complete external Action SHA set; do not pin a patch release, commit, tag object, or workflow blob in this Skill. This is authenticated run-level consistency plus signed release admission, not cryptographic job provenance; the contract defines no online or post-publication revocation guarantee, and rejection cannot undo floating-`@v1` code already executed with caller permissions. Initial activation is two-phase: publish/move `v1` and pass the live canary from the producer-only change before merging the separate consumer/Skill caller activation.
- The required-status producer caller is per-PR. Keep scheduled reconciliation in an independent repository-owned dispatcher that performs only bounded per-PR transport into that caller. The dispatcher is not producer evidence, Action-status `PASS`, or an alternate producer caller; its exact trigger, cadence, and permissions are repository implementation policy rather than generic protocol or epoch-machine inputs.
- Report `requested: triple`, `effective: double`, and the concrete reason. Do not call the result a completed triple review.
- A blocked or inconclusive local lane is not a clean double merely because the GitHub lane was unavailable.

## Common Local-Lane Contract

Codex and Claude Code use the same frozen-scope and workspace scheme. Each logical lane receives its own workspace; lanes never share a checkout or reviewer context.

For a review-policy migration that changes this playbook, its reviewer profile, prompt templates, guard, compatible-version/provenance selector, stream validator/schema, or launcher, separate review subject from review control. Candidate-head Markdown, including the frozen repo-local copy at the review head, remains readable as review subject and scoped repository guidance, but the parent must source every executable or machine-interpreted review-control component from an independently trusted bundle pinned outside `base_sha..head_sha`. Record the bundle's absolute source path, publisher-provided release identifier or frozen commit, and canonical control-file manifest SHA-256 in the lane record; verify the same digest before each launch/spawn and after each lane. Never execute candidate-head Python or shell, or load a candidate-head machine schema, to bootstrap that candidate's formal review. If the active reviewer profile or any required Claude control component cannot be bound to the manifest, the migration review is blocked. Only when the prior trusted bundle lacks a compatible new guard may that prior trusted policy review the migration before merge and release, with the new guard activated only from the resulting trusted release. The guard is non-executable source: record and revalidate a trusted absolute Python interpreter, then launch it only with `-I -B -S` and the fixed clean environment defined by the contract. It must compile the manifest-bound runtime source bytes directly without adding the bundle to `sys.path` or accepting bytecode, native extension, or same-name module substitutes. The exact manifest algorithm, interpreter evidence, default four-module closure, and profile-specific version/capability/stream source and companion closures live in [Canonical Review-Control Manifest](references/review-lane-contracts.md#canonical-review-control-manifest).

In this boundary, candidate-head Markdown is review subject and scoped guidance only; it never selects or executes the formal control plane.

The default guard profile keeps the exact four-source raw closure `review_runtime`, `review_runtime.common`, `review_runtime.claude_version_policy`, and `review_runtime.named_lane`; `preflight-claude` and `validate-claude-stream` use separate manifest-bound raw profiles for only their declared implementation/data dependencies. Companion revalidation repeats no-follow descriptor/type safety checks and compares the complete bounded content, not persistent file identity: a safe ordinary-file replacement with identical bytes is harmless. Guard-bound companion data is consumed from the immutable bytes captured by the initial validated read, never by reopening its path after final validation. These profiles never execute the env-shebang compatibility wrappers or use ordinary package import resolution.

For a scanner-recognized shape whose exact value cannot be extracted, retain bounded opaque container evidence instead: raw Git path bytes identify path containers, while the canonical blob OID alone identifies regular-file/symlink content containers; blob paths are not retained. OID multiplicity is compared independently of path and mode. One aggregate budget shared across the base, head, and optional source-WIP endpoint maps permits at most 100,000 endpoint-local identities and 16 MiB of retained path-identity bytes; a repeated identity in one endpoint increments only its integer multiplicity, and blob identities consume no path-byte budget. Unchanged containers, same-blob moves, balanced identical copies/removals, and deletions pass only when every head identity count is no greater than base; a new path identity, new or changed blob OID, or greater multiplicity is `inconclusive` only when the completed exact counter proves no violation. Defer that ordinary opaque mismatch through exact counting so it cannot suppress an independently proved exact-value growth; malformed or lost container identity, incomplete tree enumeration, unreadable bounded objects, lost count integrity, or opaque-evidence budget exhaustion remains immediately `inconclusive`.
- Complete frozen endpoint discovery/count scans retain the 64 MiB per-blob limit and charge every tree-entry blob occurrence against a 2 GiB total that matches the named-lane checkout contract. Exact occurrence counting has a separate 68 GiB search-work budget, equivalent to 32 complete fixed-pattern passes over both the 2 GiB blob envelope and the conservatively bounded 128 MiB path-metadata envelope; the generic workspace scanner retains its 16 GiB bound. They stream bounded `cat-file --batch` groups under one shared 900-second endpoint deadline, hold at most one size-bound complete blob scanner context, and scan repeated OIDs once per occurrence. Changed-location scanning retains its independent 512 MiB total.
- Report only head-side added locations for positive-delta candidates; omit unchanged occurrences. Use one-based lines for complete text evidence, `line: null` for new-path or binary fallback, and line `1` for symlink targets. Mark incomplete mapping as `location_status=inconclusive`; when endpoint trees cannot distinguish a moved occurrence from an identical new copy, omit the ambiguous locations instead of relying on heuristic rename attribution.

Run required PR/master admission directly with `isolated_review secret-admission --repo <repo> --base-ref <base_sha> --head-ref <head_sha>`. It scans the immutable Git trees under `review_contract: admission-only-no-reviewer` and does not create reviewer state, materialize a review workspace/diff/prompt, or start any provider. Exit `0` plus `temporary_cleanup_status: complete` is `clean`; exit `1` is proved violations and remains `1` even if later location mapping or temporary cleanup is incomplete; exit `75` is an inconclusive scan or a clean scan whose temporary cleanup failed. A head change invalidates the result. If an explicitly requested low-level helper run separately exists, its compatible `stateful final` and `stateful admission` results remain independent diagnostics, but neither is the required admission producer.

## Low-Level Helper Boundary

The `isolated_review` helper retains a frozen supplied-diff runtime backed by a helper-owned detached worktree and private minimal Git database for low-level compatibility and Claude runtime-security work. It records `review_contract: supplied-diff-private-git` and `named_lane_eligible: false`. Clean committed-head content is the default; only explicit `--include-source-wip` may capture staged, unstaged, and nonignored untracked content as a digest-bound diagnostic snapshot, and WIP evidence cannot satisfy PR-readiness or merge-ready exact-commit gates. Source-WIP exact-secret discovery includes the original source HEAD as well as the private snapshot and deduplicates candidates by exact raw value. When source HEAD grows over base but the private snapshot erases every proved growth, mark snapshot admission `inconclusive` with `source-head-exact-growth`; when the snapshot itself still proves exact growth, retain the normal `violations` result. Its workspace and prompt contract differ from the canonical named shapes above.

- Do not use its Codex path to satisfy single review.
- Do not count a supplied-diff helper run as the Claude Code lane of a named double/triple review.
- Do not add helper preflight, fallback, or retry attempts to the review count.
- The independent Codex supervisor never hands a child a naked retention-lock descriptor. Every handoff transfers the locked file, retention-root, and attempt-directory descriptors together with the root/path, lock identity/token, and durable `attempt_directory_binding`; the receiver revalidates the complete binding before reading or committing state. Phase and settlement helpers remain descriptor-relative to that attempt binding, and quarantine cleanup succeeds only after the original attempt name is rechecked absent.
- Its filesystem race checks are property-scoped. Security-sensitive directory custody binds `device`/`inode`/type/generation for object identity and owner/group/mode/flags plus normalized ACL/xattr evidence for access policy; directory size, link count, and timestamps are ignored because ordinary child-entry churn can change them. A permitted ACL-bearing directory may therefore change ctime while child entries change, but replacement or owner/group/mode/flags/ACL/xattr drift fails. Single-link regular-file device/inode/mode/owner protect object identity and access policy, while bounded exact reread or digest protects content stability; timestamps alone are never content evidence. Exact absence, identity/policy mismatch, and unreadable or failed revalidation remain separate outcomes.
- Before the raw checkout invokes Git, it no-follow reads the source common config and the selected linked worktree's `config.worktree`, rejects every direct `include`/`includeIf`, and rejects same-inode byte drift by exact reread. Git never consumes those mutable source configs afterward. Every source query uses a fresh private generated bare control view, while linked-worktree creation, index initialization, cleanup, and recovery use one attempt-private control view whose root identity, exact read-only config identity/bytes, and access policy are durably bound before `git worktree add --lock`. System/global config is fixed to `/dev/null`, command-scope config is fixed, the generated config omits `extensions.worktreeConfig`, and no Git command uses the source common Git directory or linked registration as its config-discovery `GIT_DIR`. The source object directory retains a device/inode/type/owner/mode binding before each Git launch; child-object churn is allowed, while object-directory replacement or access-policy drift fails. Raw object IDs and blob digests, not directory metadata, protect selected content. Missing, unreadable, policy mismatch, and revalidation mismatch remain distinct config outcomes. Every fresh query control is a canonical direct child of its owner-private recovery root: the retention root before an attempt exists and the attempt directory afterward. A closure failure carries its private-control cleanup owner and retained path into one bounded retry; successful closure runs that cleanup and releases deferred signal ownership only after closure is proved. If retry remains incomplete, the process owner no-replace publishes an owner-only canonical recovery receipt before IPC completion and deferred-signal release. The receipt binds the phase token, exact owner PID/start identity, exact Git PID/PGID/start identity when anchored, and a bounded list containing only direct-child `codex-git-control-*` paths; the list is empty when the already bound attempt-private control is the only recovery locator. A pre-attempt receipt is stored inside the retained control root and returned as structured recovery metadata. Checkout, prequiescence-abort cleanup, and final-cleanup receipts use the fixed attempt-private receipt path. After closure/receipt handling, the outer path first completes custody and child-supervisor quiescence, then forces the deferred-signal checkpoint before any prequiescence state or worktree mutation; a closure created inside prequiescence cleanup checkpoints immediately after its fixed receipt. The worker failure record and the attempt supervisor's non-success terminal summary use closed schemas. The parent reaps the worker before validating either the IPC record or durable receipt; malformed, missing, conflicting, or publication-failed evidence remains an explicit closure gap and disables later worktree mutation or cleanup. After the exact attempt supervisor is reaped with exit 2, the outer supervisor derives the result only from the current nonterminal durable attempt state and fixed receipt even when terminal IPC is missing or malformed; damaged IPC never supplies authority. Exit-0/1 still requires an exact terminal envelope whose summary equals durable terminal state. The per-attempt lock-reason token lets recovery adopt only the exact locked private registration after a crash.
- The app-server JSON wire contract admits only `null`, booleans, strings, arrays, objects, and int64 integers. Every floating-point token is rejected by `parse_float` before conversion, including normal, subnormal, overflow, and underflow spellings; outbound Python floats are rejected by the same tree contract.
- For helper-only Claude diagnostics, use `explicit-claude-review`; use `explicit-claude-with-copilot-fallback` only after separate user consent explicitly authorizes both destinations. Named `double`/`triple` phrases and legacy `double-review`/`triple-review` values are not low-level helper consent markers.
- For helper authentication, apply precedence `ANTHROPIC_API_KEY` > `CLAUDE_CODE_OAUTH_TOKEN` > local login and opaque-forward only the winning explicit value. An explicit API key or OAuth token bypasses helper local-login carrier access and its refresh transaction. For a catalogued local-login artifact, acquire the certified host refresh locks before the first credential read and retain one outer transaction lease through credential exposure, reviewer/broker quiescence, rotation persistence, and final verification. Release only after quiescence and persistence are proven; otherwise retain descriptor-bound stale-fence evidence and pause without automatic deletion or Copilot fallback.
- Intentionally retained shared refresh-lock directories never authorize a lexical recovery or cleanup pathname; report only descriptor-bound residue.
- The low-level helper accepts publisher-verified Claude Code versions `>=2.1.211,<3.0.0`, but local-login refresh writeback additionally requires an exact signed artifact in its credential-lock catalog. An uncatalogued in-range artifact therefore blocks only helper local-login; helper API-key/OAuth modes and the named direct lane remain governed by the full compatible range. The helper does not run an OAuth freshness warmup: an expired local-login access token may refresh inside the isolated carrier, while `Login expired`, HTTP 401, or refresh failure pauses and directs the user to reauthenticate. Authentication failure never authorizes Copilot.
- Pass helper Claude raw stdout through the same preflight-bound strict validator used by the direct lane. Preserve its machine classification exactly; broker/carrier success, prose inspection, or partial output never supplies findings or authorizes fallback.
- Read [helper-contract.md](references/helper-contract.md) before modifying or debugging the helper.
- Read [claude-runtime-trust.md](references/claude-runtime-trust.md) before changing the helper's version, provenance, platform, sandbox, capability-probe, carrier, or refresh-transaction behavior.

## Guardrails

- Do not precompute a full diff for a named local lane, even when it seems convenient or the change is small.
- Do not run formal review against a live dirty working tree. Create an explicit review anchor only when the parent request authorizes that mutation; otherwise stop as `blocked-authorization`.
- Do not claim clean review without a trustworthy terminal artifact for every required lane in the effective shape.
- Do not treat validator acceptance as a clean outcome, normalize the raw result, or let prose inspection substitute for artifact validation.
- Do not automatically rerun a lane because its presentation is extended, contradictory, ambiguous, or otherwise non-canonical. Rerun only for invalidated range/head evidence, a finding fix on a new head, or an explicit request.
- Do not treat an exact-App check/run as the GitHub lane's terminal artifact or no-findings payload; its role is service-start evidence only. Do not let a noncanonical repository-side compatibility Commit Status satisfy the separately bound required `codex/review-gate` status.
- Do not report a requested triple as completed triple after GitHub Codex fallback.
- Do not silently replace Claude Code with another provider.
- Do not downgrade a model for capacity, timeout, network, or other transient failure.
- Do not infer entitlement from silent model substitution.
- Do not follow a CLI-reported persisted/spilled-output path outside the Claude worktree. Use absolute `Read.file_path` and present `Grep.path` / `Glob.path` values; keep required `Glob.pattern` relative, parent-free, home-shorthand-free, and extglob-free. Ordinary recursive, intermediate-component, character-class, and bounded simple brace patterns such as `**/*.py` and `src/**/*.{py,md}` are allowed, as are leading forms such as `./**/*.py`; intermediate `.` is not. Rerun a narrower bounded worktree-scoped command; an observed structured outside-workspace tool read invalidates the lane.
- Do not start another reviewer from a findings-only review child.
- Do not use state-changing MCP, Plugin, Git, or GitHub actions inside a review-only lane.
- Do not block trusted reviewer launch on a tracked secret delta or redact tracked reviewer input based on admission status.
- Do not count encoded variants for admission; enforce only the complete-tree global exact-raw-value non-growth rule.
- Do not require or start a low-level helper reviewer to produce PR/master admission; use the direct admission-only command. Do not treat `stateful final` as secret-admission evidence or merge the two terminal decisions when helper compatibility state exists.
